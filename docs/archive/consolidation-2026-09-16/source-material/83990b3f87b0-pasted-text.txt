# CatchGrid Bug-Tester Readiness Pass

Work in the existing CatchGrid repository:

`HoLeeChuck/dexly-pokemon-go-companion`

## Objective

Prepare the current CatchGrid website for a small group of real-world bug testers.

This is **not** an accessibility remediation pass and it is **not** a redesign of the entire application.

The priority is:

1. Make the primary collection workflows coherent.
2. Fix confusing or broken website behavior.
3. Protect tester collection data.
4. Make navigation and state preservation feel reliable.
5. Remove duplicated or misleading functionality.
6. Make the application stable enough that tester feedback is about the product rather than obvious implementation problems.

Do not overengineer this work.

Preserve the existing local-first architecture, collection data, stable IDs, import/export compatibility, catalog structure, artwork policy, themes, and existing working functionality unless a task below explicitly requires changing it.

## Important constraints

* Do not change stable Pokémon/form IDs.
* Do not perform unnecessary data migrations.
* Do not replace the repository-local Pokémon HOME artwork system.
* Do not introduce runtime artwork hotlinking.
* Do not change the fundamental local-first collection model.
* Do not rewrite large areas of the application unnecessarily.
* Reuse existing components and utilities where practical.
* Preserve current user collection data.
* Preserve existing backup/import/export compatibility.
* Keep existing light/dark modes and accent themes working.
* Accessibility improvements are **not a priority for this pass**.
* However, do not knowingly introduce new accessibility regressions while making these changes.

---

# 1. Consolidate Progress and Search Lab

The current Search Lab overlaps too much with Progress.

The long-term product structure should be:

* Home
* Dex
* Progress
* Settings

Search Lab should no longer remain a separate primary destination.

## Move useful Search Lab functionality into Progress

Integrate the useful existing tools into Progress, including where currently supported:

* Missing Pokémon search strings
* Collection-aware storage searches
* Personal search strings
* Trade-oriented search strings
* Discord/share output
* Copyable Pokémon GO search strings

Do not throw away existing Search Lab functionality unnecessarily.

Reuse its logic where possible rather than rewriting it.

## Desired Progress structure

Progress should roughly follow:

1. Overall collection summary
2. Regional progress
3. Personal/storage search tools
4. Missing-Dex/search-string generator
5. Trade/share tools
6. Discord/share output

The exact visual layout can follow the existing design system.

## Search Lab route

Once its useful functionality has been moved:

* Remove Search Lab from primary navigation.
* Redirect the old Search Lab route to Progress.
* Preserve reasonable backward compatibility for old links.

## Home links

Update Home shortcuts so actions like:

* Find Missing Pokémon
* Search My Storage
* Generate Search Strings

lead to the correct Progress section instead of sending users somewhere misleading.

---

# 2. Improve Dex State Preservation

The Dex should feel like a persistent workspace.

Currently users can lose context when navigating away and returning.

Preserve appropriate Dex state, including:

* Search query
* Region filter
* Collection/category filter
* Form/view selection
* Quick Check mode
* Relevant filter state
* Internal Dex scroll position

If practical, put shareable/filterable state in the URL.

Use session/application state for temporary UI state where URL state would be inappropriate.

Important:

The Dex uses its own internal scrolling container, so restoring only `window.scrollY` is not sufficient.

Expected behavior:

A tester should be able to:

1. Search for something.
2. Apply filters.
3. Scroll deep into the Dex.
4. Open a Pokémon.
5. Navigate elsewhere.
6. Return to Dex.

…and remain close to where they were instead of starting over.

---

# 3. Separate Collection Category From Form View

The current Dex selector mixes concepts such as:

* Normal
* Shiny
* Lucky
* 100%
* Mega
* Gigantamax

These are not all the same kind of filter.

Separate them conceptually.

## Collection Category

Examples:

* Normal
* Shiny
* ★ 100%
* Lucky
* XXL
* XXS
* Shadow
* Purified

Use the black star character for 100%, not an emoji.

## Form View

Examples:

* Species
* Mega / Primal
* Gigantamax

If additional transformation/form views already exist and fit naturally, support them appropriately.

Changing Form View must not silently reset Collection Category unless there is a genuinely unavoidable compatibility reason.

Avoid unnecessary redesign. The goal is simply to make the controls understandable.

---

# 4. Improve Form Search

The Dex should be able to find alternate/collector forms by their displayed names or aliases.

Currently many forms are primarily discoverable only by opening the parent species.

Improve search indexing so a tester can search for a known form directly.

Examples could include:

* Regional forms
* Named alternate forms
* Collector/costume forms already present in the catalog
* Mega forms
* Other supported form display names

Keep the main Dex species-first if that is the current design.

Do not turn the entire Dex into a giant flat 1,269-form grid unless the architecture already supports that naturally.

Instead, make form search results discoverable and understandable.

---

# 5. Fix Quick Check Dead Cards

In Quick Check mode, Pokémon that cannot be toggled should not become useless/dead cards.

Expected behavior:

* If the selected category can be toggled, Quick Check can perform the existing quick toggle.
* If the category is unavailable/ineligible, clicking the card should still allow the user to open the Pokémon details.
* Do not mutate unavailable states.

This allows testers to understand why something cannot be collected.

---

# 6. Improve Pokémon Detail Behavior

## Previous / Next Navigation

Previous/next navigation should follow the context the user was browsing.

Example:

If a user filtered the Dex to a subset and opens Pokémon #20, Next should generally move to the next Pokémon in that filtered result set, not simply the next National Dex species.

Pass the originating result context into the detail view where practical.

For alternate forms opened from inside a species-specific form list, either:

* keep navigation within the appropriate form context, or
* hide previous/next if there is no sensible browsing context.

Do not allow navigation to feel random.

## Explain Disabled Categories

If a collection option is disabled, explain why.

Examples:

* Shiny not released
* Not eligible for Shadow
* Mega form unavailable
* Gigantamax unavailable
* Data unavailable / needs review

Avoid showing a disabled control with no explanation.

## Long Names

Make long Pokémon/form/costume names readable.

Avoid aggressive single-line truncation where the actual identity of the form becomes unclear.

Allow wrapping or split:

* Pokémon name
* Form qualifier

Test particularly at:

* 360px mobile
* 390px mobile
* tablet widths

## Representative Artwork

Some forms use representative artwork.

Make that visible to users instead of relying on a hover tooltip.

A small text badge or note such as:

`Representative art`

is sufficient.

Do not change the artwork source.

# 7. Clarify Progress Counts

Progress currently risks mixing:

* National Dex species
* Collector forms
* Alternate forms
* Transformations

Make the denominator/scope clear.

If the current overall number only counts default species, label it clearly.

For example:

`National Dex species progress`

Do not imply that this number represents every collectible form if it does not.

If the existing architecture makes it easy to show additional breakdowns, useful categories could include:

* Species
* Forms
* Transformations

But do not create a major new statistics system just for this pass.

Clarity is more important than adding more metrics.

---

# 8. Fix Regional Progress Category Counts

Regional progress should respect the currently selected collection category.

If the user switches from:

Normal

to:

Shiny

the regional cards/counts should not continue showing Normal counts without explanation.

Either:

* update the region cards based on the active category, or
* clearly label the region card counts as Normal-only.

Prefer updating them to match the selected category if the data model already supports this cleanly.

---

# 9. Clean Up Settings Information Architecture

Settings should prioritize common tasks.

Desired broad order:

1. Collection Setup
2. Appearance
3. Import Collection
4. Export & Backups
5. Data Management
6. Advanced regional/Vivillon information
7. About

Do not necessarily use these exact headings if current components already have appropriate names.

The important point is that regional/Vivillon reference material should not dominate the top of Settings.

Move advanced regional information lower on the page or into a collapsed/advanced section where appropriate.

---

# 10. Fix Approximate Location Feature

The current regional availability UI offers an approximate-location feature using browser geolocation.

The production permissions policy currently disables geolocation.

Resolve this mismatch.

Choose the cleanest option:

### Option A — Keep the feature

Allow same-origin geolocation through the site's permissions policy.

Continue converting the position into a coarse region locally.

Do not retain raw coordinates unnecessarily.

### Option B — Remove/disable the button

If geolocation is not actually needed for the tester release, remove or disable the feature instead of presenting a button that cannot work.

Do not leave a known broken control in the tester build.

---

# 11. Make CSV Import Review Trustworthy

The CSV import preview currently truncates what the user sees.

Examples from the current implementation include limited subsets of:

* issues
* changes

while the action still implies the import has been fully reviewed.

Improve this.

At minimum show:

* total number of changes
* total number of issues
* how many are currently visible

Example:

`Showing 12 of 184 changes`

Prefer allowing the tester to inspect the complete set using something reasonable such as:

* expandable sections
* pagination
* virtualized list
* filters

Do not dump hundreds of rows into an unusable page.

Any genuinely blocking import issues must prevent Apply.

The user should know what they are accepting before modifying their collection.

---

# 12. Add Backup Restore Preview / Confirmation

Selecting a JSON backup file should not immediately replace collection data.

Recovery snapshot restore should also not immediately overwrite data.

Create a two-stage restore flow.

## Stage 1 — Review

Show useful information where available:

* backup creation date
* catalog version
* compatibility status
* number of collection records
* saved searches
* settings that will be restored
* whether existing collection data will be replaced

## Stage 2 — Confirm

Require an explicit confirmation before applying the restore.

If the current restore system automatically creates a pre-restore snapshot, keep that protection and explain it.

Expected behavior:

Selecting the file itself must not mutate the collection.

---

# 13. Notification Cleanup

Prevent notifications from fighting each other.

Current examples include:

* normal application toasts
* service-worker update prompts

Ensure multiple bottom-of-screen messages do not overlap or cover important controls.

Use one coordinated notification area or appropriate stacking.

Do not redesign the entire toast system if a small layout/state fix is enough.

---

# 14. Offline / Update Reliability

Review the service-worker behavior for public routes.

Currently lazy route chunks may only become available offline after being visited online.

Ensure the main public application routes behave reasonably offline.

Public routes:

* Home
* Dex
* Progress
* Settings

After Search Lab consolidation, its old route can simply redirect appropriately.

Ideal behavior:

After installing/loading the application normally, the major public routes should not unexpectedly fail just because the user has not visited that particular route previously.

If complete route precaching is reasonable, implement it.

Do not precache the entire Pokémon artwork library.

Continue caching artwork on demand.
