# CatchGrid Legacy Cleanup and Optimization

Act as a senior React, TypeScript, Cloudflare Workers, and repository-maintenance engineer. Perform a careful cleanup and optimization pass on the CatchGrid Pokémon GO companion.

## Repository

GitHub repository:

`https://github.com/HoLeeChuck/dexly-pokemon-go-companion`

Production site:

`https://dex.cjdev.app/`

## Primary objective

Identify and remove genuinely unused, retired, duplicated, or redundant code while preserving all intentional compatibility, user-data migration, recovery, production deployment, and Cloudflare infrastructure behavior.

This is an implementation task, not only an audit. Make the code changes, add or update tests, validate the result, push the work to a dedicated branch, and open a pull request for review.

Do not merge the pull request.

## Required Git workflow

1. Fetch the latest remote repository state.

2. Start from the latest `main`.

3. Confirm the current commit SHA before making changes.

4. Create a new branch named:

   `codex/catchgrid-cleanup-optimization`

5. Keep commits logically separated by cleanup category.

6. Push the branch.

7. Open a draft pull request targeting `main`.

8. Do not merge it.

Do not rewrite existing migration history or force-push shared branches.

Use shared constants rather than repeating category and theme values.

At minimum:

* Introduce or centralize an `ACCENT_THEME_IDS` constant.

Avoid introducing a large or fragile build system solely for this small constant.

# Phase 2 — Refactor the oversized application shell

`src/App.tsx` currently owns too many unrelated responsibilities. Refactor it without changing product behavior.

## Required separation

Move cohesive responsibilities into focused modules or hooks. A reasonable target structure is:

```text
src/
  app/
    routing.ts
    AppShell.tsx
    useAppNavigation.ts
    usePwaUpdates.ts
  catalog/
    catalogIndex.ts
    regionMedals.ts
    useCatalogView.ts
  profile/
    useLocalProfile.ts
    useCollectionMutations.ts
    usePortableBackups.ts
    useProfileRecovery.ts
  owner/
    OwnerRoute.tsx
    ownerApi.ts
    useOwnerProfile.ts
  routes/
    HomeRoute.tsx
    DexRoute.tsx
    SearchRoute.tsx
    ProfileRoute.tsx
```

The exact names may differ, but the resulting architecture must:

* Reduce the responsibilities and size of `App.tsx`.
* Keep routing behavior identical.
* Keep scroll restoration behavior identical.
* Preserve recovery, owner access, import, export, and PWA update behavior.
* Avoid moving complexity into a single equally oversized replacement module.

Do not add a routing dependency unless there is a clear benefit that outweighs the migration risk. The current hash and `/cody` routing may remain custom.

# Phase 3 — Route-level code splitting

Create real route boundaries using `React.lazy`, dynamic imports, or equivalent Vite-supported splitting.

At minimum, evaluate lazy-loading:

* Dex route
* Search Lab route
* Profile/Data route
* Owner `/cody` route
* Pokémon detail sheet
* Backup and restore utilities
* Owner API and import utilities

The Home route may remain eager if it is the default route.

## Important requirement

Simply lazy-loading a component is insufficient if all supporting owner, import, backup, and migration logic remains imported by `App.tsx`.

Move route-specific code behind the lazy boundary so that it is not present in the initial public bundle.

The private `/cody` route should not cause normal public visitors to download:

* Owner authentication UI
* Owner mutation API methods
* Cloud CSV import logic
* Private backup logic that is not needed by the public profile
* Legacy D1 workflow code used only by the owner route

Do not break public local-profile backup and recovery functionality. Distinguish public profile portability from private owner/D1 functionality.

# Phase 4 — Catalog computation optimization

Create a memoized catalog index instead of repeatedly scanning the complete catalog on unrelated renders.

A possible shape is:

```ts
interface CatalogIndex {
  defaultForms: readonly CatalogItem[];
  regions: readonly string[];
  formsByRegion: ReadonlyMap<string, readonly CatalogItem[]>;
  formsByVariant: ReadonlyMap<string, readonly CatalogItem[]>;
  formsBySpecies: ReadonlyMap<string, readonly CatalogItem[]>;
  formsById: ReadonlyMap<string, CatalogItem>;
}
```

Use the index to optimize:

* Default National Dex filtering
* Mega and Primal filtering
* Gigantamax filtering
* Region lists
* Region medal calculations
* Species form lookup
* Detail-sheet previous and next navigation
* Search and collection filtering

Memoize calculations using the smallest correct dependency set.

Avoid premature micro-optimization. The goals are:

* Eliminate obvious repeated full-catalog scans.
* Centralize catalog derivation.
* Improve code clarity.
* Preserve deterministic behavior.

# Phase 5 — API boundary cleanup

Suggested modules:

```text

  request.ts
  publicCatalogApi.ts
  collectionApi.ts
  ownerApi.ts
  legacyTradeApi.ts
```

Requirements:

* The public catalog route should import only public catalog functions.
* Collection mutations should be separate from owner/import operations.

* Worker trade endpoints may remain for backward compatibility.
* Preserve existing error-envelope behavior and typed `ApiClientError`.

Delete inactive client API methods only when they are proven unused and their removal does not break migration, owner, or test workflows.

# Phase 6 — CSS organization and reduction

`src/styles.css` is a large global stylesheet.

After removing dead selectors:

* Split CSS by route or feature where Vite can associate styles with lazy-loaded modules.
* Keep truly global variables, resets, typography, focus behavior, buttons, and app-shell rules in a global stylesheet.
* Move Dex-specific styles into the Dex route.
* Move Search Lab styles into the Search route.
* Move Profile/Data styles into the Profile route.
* Move owner-only styles into the Owner route.
* Move detail-sheet styles with the detail component.

Do not convert the entire project to CSS Modules or another styling system unless that is demonstrably safer and simpler than the current architecture.

Preserve:

* Light and dark themes
* All accent themes
* Reduced-motion handling
* Responsive behavior
* 320-pixel minimum layout
* 44-pixel touch targets
* Focus-visible states
* Safe-area handling
* Existing accessibility semantics

Record before-and-after generated CSS sizes.

# Phase 7 — Service-worker optimization

The current service worker precaches generated JavaScript and CSS assets.

After introducing route chunks:

* Do not automatically precache every lazy route chunk unless it is necessary for the offline contract.
* Precache the application shell and critical default-route assets.
* Runtime-cache lazy route chunks after they are visited.
* Continue excluding:

  * Private API responses
  * Owner `/cody` navigation
  * Owner data
  * Mutation endpoints
* Preserve explicit update acceptance through `SKIP_WAITING`.
* Preserve offline navigation fallback.
* Preserve catalog fallback behavior.
* Ensure private responses never enter caches.

Add or update PWA tests covering:

* Initial service-worker install
* Waiting update prompt
* User-approved update
* Offline Home
* Offline Dex after it has been visited
* Lazy route chunk loading
* Owner route exclusion
* Private API exclusion
* Catalog cache fallback

# Phase 8 — Build configuration cleanup

## Vite public-directory copying

Inspect the custom `writeBundle()` copying logic in `vite.config.ts`.

Vite normally copies `public/` assets into the output directory. Determine whether the project’s custom copying duplicates Vite’s existing behavior.

Perform a controlled comparison:

1. Build the current configuration.
2. Record the complete `dist/client` file list and hashes.
3. Test a branch-local version without redundant manual copies.
4. Compare the output.
5. Remove only copying that is proven redundant.
6. Preserve the custom service-worker version and generated-asset injection.

Do not change production output paths without updating Cloudflare deployment and tests.

## Double production build

Inspect the release commands in `package.json`.

The current release process appears to build during preflight and then build again before deployment. Refactor toward:

```text
validate source
→ build one final artifact with final release metadata
→ validate that exact artifact
→ deploy that exact artifact
→ smoke test
```

Requirements:

* The artifact validated by dry-run should be the artifact deployed.
* Build metadata must remain accurate.
* The process must still create the D1 Time Travel bookmark before migration.
* Production migration ordering must remain safe.
* Rollback commands must remain available.
* Do not reduce release safety merely to save build time.

Update deployment documentation when command behavior changes.
