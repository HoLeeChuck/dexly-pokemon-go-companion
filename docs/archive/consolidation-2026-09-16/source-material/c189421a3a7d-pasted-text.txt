## 4.1 Trade

### Default string

```text
#trade&
```

### Explanation

This is a quick shortcut into Pokémon the user has already marked as available for trading.

The trailing `&` is intentional.

It allows the user to tap/copy the string and immediately append another Pokémon GO search term without first typing another separator.

Example:

```text
#trade&pikachu
```

### Custom tag explanation

Make it clear that `trade` is only the tag name Cody uses.

The user may use any Pokémon GO tag name they prefer.

For example, some users may use:

```text
#adoption&
```

The UI text should explain that the user can replace `trade` with their own trade-storage tag.

Do not hard-code language suggesting the tag must literally be named `trade`.

---

## 4.2 Megas

### Default string

```text
#max&mega2-3&
```

### Purpose

This search is meant to show Pokémon the user intentionally keeps in their active Mega rotation.

`mega2-3` finds Pokémon at Mega Level 2 or Mega Level 3.

The custom `#max` tag prevents the results from becoming cluttered with Pokémon that technically have Mega Level 1 unlocked but are not Pokémon the user actually intends to keep Mega evolving.

### Important context for the write-up

With newer Super Mega Raid catches, Pokémon may already have Mega Level 1 unlocked.

Because of that, a broad Mega search can include many Pokémon the user does not actually want to keep Mega evolving.

Using a custom tag such as:

```text
#max
```

allows the user to deliberately mark only the Mega Pokémon they care about.

### Custom tag explanation

Make it clear that `max` is simply Cody’s chosen tag name.

Users can choose any custom tag name.

However:

**Recommend avoiding the tag name `mega`.**

Pokémon GO already uses `mega` as part of its built-in search syntax, so using `mega` as a custom tag name can create confusing or conflicting searches.

The explanatory copy should explicitly mention this.

## 4.3 Tag

### Exact string

```text
!#&4*,shiny,costume,background,candykm20,dynamax,gigantamax,lucky&
```

### Purpose

This helps identify valuable or unusual Pokémon that currently have no tag assigned.

The search combines untagged Pokémon with several categories that are commonly worth reviewing and organizing:

- 4-star
- shiny
- costume
- background
- 20 km buddy-distance Pokémon
- Dynamax
- Gigantamax
- lucky

The trailing `&` remains intentional so the user may append another condition.

This search is intended as a tagging/organization review.

---

## 4.4 Evolve

### Exact string

```text
!#&evolvenew&
```

### Purpose

Find untagged Pokémon that can evolve into a Pokédex entry the player has not registered yet.

This is useful for checking storage before transferring Pokémon and for identifying easy evolution-based Pokédex progress.

Keep the explanation concise because the search is largely self-explanatory.

---

## 4.5 Special Moves

### Exact string

```text
!#&@frustration,@return,@special&
```

### Purpose

Find untagged Pokémon with move-related conditions that deserve review before transferring or organizing them.

This includes:

- Frustration
- Return
- special/legacy move results returned by Pokémon GO's `@special` search

This acts as a safety/review search for Pokémon with moves the user may want to preserve or tag.

---

## 4.6 Untagged

### Exact string

```text
!#&
```

### Purpose

This is the simplest cleanup search.

It finds Pokémon with no tag assigned.

The trailing `&` lets the user immediately add another filter.

Example:

```text
!#&kanto
```

Keep this write-up simple.

# 5. Dynamic XXL recommendation

XXL should remain dynamically generated from CatchGrid collection data.

The purpose is to help the user search Pokémon GO storage for **untagged XXL Pokémon that could contribute toward missing XXL collection entries**.

The generated string should begin with:

```text
!#&xxl&
```

Then append the dynamically generated Pokédex-number portion.

Example structure only:

```text
!#&xxl&001-003,006,009
```

Do not hard-code the example numbers.

Use the actual user collection state.

## Evolution-aware behavior

Preserve or implement the previously discussed evolution-aware behavior.

If the user is missing an XXL entry for an evolved Pokémon, an earlier evolutionary stage should also be included when evolving that Pokémon could satisfy the missing XXL entry.

Example concept:

If the user needs an XXL Charizard, an eligible XXL Charmander or Charmeleon may also be useful.

The generated number set should therefore account for useful evolutionary predecessors where appropriate.

Requirements:

- derive data from CatchGrid collection state
- exclude unavailable/unreleased entries where appropriate
- use deterministic Pokédex order
- compress consecutive Pokédex numbers into ranges
- avoid duplicates
- update automatically when collection state changes
- retain the `!#&xxl&` prefix
