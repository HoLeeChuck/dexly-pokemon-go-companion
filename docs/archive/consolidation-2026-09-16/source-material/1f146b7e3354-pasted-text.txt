# CatchGrid Redesign and Development Plan

You are working inside the existing CatchGrid repository.

CatchGrid is a Pokémon GO collection companion that lets users track Pokémon and collectible states such as Normal, Shiny, Lucky, Hundo, XXL, XXS, Shadow, Purified, alternate forms, Mega evolutions, and Gigantamax forms.

Your task is to implement the product and UX restructuring described below. Improve the existing application rather than rebuilding it from scratch.

## Primary objective

Restructure CatchGrid around four clearly defined areas:

1. **Home** — introduction, onboarding, feature discovery, and useful shortcuts
2. **Dex** — browse Pokémon and update collection states
3. **Progress** — view completion, identify missing Pokémon, generate search strings, and share missing lists
4. **Settings** — configure tracking, bulk-update collection data, manage appearance, import, export, and backups

The final application should feel like one connected workflow:

> Learn on Home → Track in Dex → Act on missing entries in Progress → Configure and protect data in Settings

---

# Non-negotiable implementation rules

## Preserve existing behavior and data

- Do not replace the existing application with a disconnected redesign.
- Preserve all working collection tracking, persistence, import, export, backup, recovery, filtering, and Pokémon data behavior.
- Do not introduce fake production data.
- Do not replace real values with hard-coded mock statistics.
- Do not silently discard existing browser collection data.
- Do not change import or export formats without providing backward-compatible parsing or a clear migration.
- Reuse the existing design system, theme tokens, components, icons, typography, Pokémon assets, and data sources where practical.
- Keep the existing CatchGrid visual identity, especially its purple color system, while improving hierarchy and usability.
- Do not copy the Pokémon GO or Pokémon GO Database screenshots literally. Use them only as interaction and information-architecture references.

## Audit before changing code

Before implementing, inspect and document:

- Framework and routing structure
- Main application shell and navigation components
- Home, Dex, Search Lab, Profile, and related routes
- Pokémon detail dialog implementation
- Current collection-state data model
- Species, forms, transformations, costume, availability, and region metadata
- Existing search-string generator logic
- Existing import and export schemas
- Local-storage, IndexedDB, browser backup, or other persistence logic
- Current responsive breakpoints
- Existing tests
- Existing portfolio, application version, and legal metadata
- Existing icon and sprite sources

Identify the minimum safe set of files and data migrations required.

After the audit, proceed with implementation. Do not stop after only providing recommendations unless a genuine repository limitation prevents progress.

# Progress page redesign

Progress should become the central place where users:

- See what they are missing
- Review regional completion
- Generate collection-aware Pokémon GO search strings
- Generate trade-oriented strings
- Share missing lists with friends

The page should flow from high-level information to detailed actions.

## Required Progress page order

1. Overall collection summary
2. Regional progress cards
3. Global personal search strings
4. Missing-Dex generator
5. Share with friends

## Overall collection summary

Display completion across currently supported tracking categories, including where available:

- Normal
- Shiny
- Lucky
- Hundo
- XXL
- XXS
- Shadow
- Purified

Use real collection and availability data.

Do not count unreleased or unavailable entries as obtainable missing entries unless the current application intentionally defines completion differently.

Where possible, distinguish between:

- Collected
- Missing
- Unreleased
- Currently unavailable
- Event-limited

Completion totals should be trustworthy and explainable.

## Regional progress cards

Display one clickable card for each region supported by the existing data model.

Do not hard-code unsupported regions.

Each card should show:

- Region name
- Overall count
- Relevant category completion
- A clear indication that the card opens a detailed view

The current compact region-card concept can be retained and improved.

Clicking a region must open a dedicated regional progress route or subpage.

Preserve selected region state in the URL where the router supports it.

## Regional progress pages

Each regional page should allow users to:

- Review progress for that region
- Select a collection category
- View missing Pokémon
- Copy a personal search string
- Copy a trade-oriented string
- Open a missing Pokémon directly in the Dex or Pokémon detail view

Category sections should include the actual completion count and actionable controls.

Example actions:

- View Missing
- Search My Storage
- Send to a Friend
- Copy

Do not make the user construct Pokémon GO strings manually.

## Global personal search strings

On the main Progress page, generate strings using the user’s complete collection rather than only one region.

One important use case is a string that can be saved as a Favorite inside Pokémon GO and used to surface Pokémon the user still needs for categories such as XXL or XXS.

The intended conceptual behavior includes strings similar to:

`!#&xxl,xxs&001-003,...`

Treat examples as product intent, not guaranteed final syntax.

The generator must derive exact syntax from the existing implementation, tests, and validated Pokémon GO search behavior. Do not guess operators or logical precedence.

Clearly distinguish:

- **Search My Storage** — designed for the current user
- **Send to a Friend** — designed for another player to paste into their account

## Missing-Dex generator

Toward the bottom of Progress, implement a section that includes cards for:

- Normal
- Shiny
- XXL
- XXS

Each card should display:

- Category label
- Number missing
- Generated Pokémon GO search string
- Copy button

The generator should:

- Use the current user’s collection data
- Exclude unavailable entries where appropriate
- Sort by Pokédex number
- Compress consecutive Pokédex numbers into ranges where valid
- Produce deterministic output
- Update when collection data changes
- Handle empty results gracefully
- Avoid showing stale generated strings

Use inline copy confirmation:

- Copy
- Copied

Do not display a global toast for copy confirmation.

## Trade strings

Support strings designed to be sent to another player.

The intended behavior includes strings conceptually beginning with filters such as:

`!traded&001-...`

Do not assume this exact syntax is correct without validating it against the existing generator or documented application logic.

The UI must clearly state:

- Who should paste the string
- What it is expected to find
- Which category it represents
- How many species are included

## Share with friends

Below the Missing-Dex generator, add the Discord-ready sharing interface.

Users should be able to select which categories to include:

- Normal
- Shiny
- XXL
- XXS

The generated sharing output should:

- Include missing counts
- Include appropriately formatted strings
- Use readable headings
- Use code blocks where appropriate
- Split safely when a message exceeds the configured character limit
- Preserve complete code fences when splitting
- Indicate how many messages will be generated
- Allow individual messages to be copied
- Allow the complete share output to be copied

Use the existing platform limit if one already exists. If the current interface treats Discord’s limit as 2,000 characters, centralize that value instead of duplicating it.

Convert the current Profile/Data page into a true Settings page.

## Single-column layout

Replace the current two-column layout with one readable vertical column.

Use an appropriate maximum content width so controls remain readable on large displays, but do not leave a mostly empty main column beside a narrow settings column.

1. Collection Setup
2. Appearance
3. Import Collection
4. Export and Backups
5. Data Management
6. About CatchGrid

The current large import-focused hero should be replaced with a simpler Settings header and concise description.

## Collection Setup

Add a section for bulk regional completion.

The purpose is to support users who already have most of their Pokédex and prefer to work backward by unmarking missing Pokémon.

For each supported region, provide an action such as:

- Mark Kanto complete
- Mark Johto complete
- Mark Hoenn complete

The exact region list must come from existing metadata.

### Bulk-completion rules

By default, marking a region complete should affect only the **Normal** collection state.

It must not automatically mark:

- Shiny
- Lucky
- Hundo
- XXL
- XXS
- Shadow
- Purified
- Mega
- Gigantamax

Only mark valid, obtainable Normal entries according to the existing availability model.

Before applying the change, show a confirmation explaining:

- Which region will be changed
- Which category will be marked
- How many entries will be affected
- That individual Pokémon can be changed afterward

Provide a reversible action, such as clearing the region’s Normal states.

Use transactional or batched state updates so hundreds of individual writes do not leave the collection partially updated.

## Tracked categories

Where the architecture allows it without destabilizing persistence, add a Settings section that lets users choose which optional categories they actively track.

Potential optional categories:

- Lucky
- Hundo
- XXL
- XXS
- Shadow
- Purified

Shiny may remain enabled by default.

Disabled categories should be hidden from:

- Pokémon detail controls
- Progress summaries

Do not delete the user’s saved state when a category is hidden.

If this addition would require an unsafe schema change, implement the foundation and document the remaining migration work rather than silently breaking saved data.

Preserve existing:

- Stored appearance preferences

Do not leave a Light Mode button in desktop or mobile navigation.

## Import, export, and backups

## About CatchGrid

Do not guess Pokémon GO syntax.

Inspect:

- Existing Search Lab logic

- Existing tests
- Existing saved search behavior

- Ordered Pokédex numbers
- Consecutive range compression
- Individual-number lists
- Normal missing lists
- Shiny missing lists
- XXL and XXS missing lists
- Trade-oriented lists
- Region-limited output
- Global output
- Availability filtering
- Empty results
- String length limits
- Multi-message splitting

Add focused tests for:

- One entry
- Multiple non-consecutive entries
- Consecutive ranges
- Mixed ranges and individual values
- Regional boundaries
- Unavailable entries
- Shiny
- XXL
- XXS
- Traded versus not-traded intent
- Zero missing entries
- Maximum-length output
- Safe Discord message splitting
- Stable deterministic output

Each generated result should expose structured metadata such as:

- Generated string
- Number of species
- Category
- Intended recipient or usage
- Region scope

# Performance

The National Dex and its forms may create a large number of rendered elements.

Preserve or add sensible optimizations:

- Lazy-load Pokémon sprites
- Debounce text search
- Memoize expensive filtering and progress calculations
- Avoid recalculating every progress category after an unrelated UI change
- Batch regional bulk updates
- Avoid rerendering the entire Dex after one collection toggle
- Use virtualization or pagination only where it meaningfully improves the current application
- Do not introduce heavy dependencies for small UI needs

Measure before adding unnecessary complexity.
