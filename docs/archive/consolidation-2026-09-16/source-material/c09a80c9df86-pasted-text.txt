PRODUCT PRINCIPLE

This should feel like a mobile Pokédex, not a spreadsheet.

The primary collection interface should be a visual three-column Pokémon grid inspired by the Pokémon GO Pokédex experience. It should be optimized for quickly seeing what is collected, what is missing, and checking entries off.

Core collection categories include:

- Normal
- Shiny
- Lucky
- Hundo / Perfect
- XXL
- XXS
- Shadow
- Purified

The data model must be extensible for:

- Nundo
- Dynamax
- Gigantamax
- Mega
- Costumes
- Regional forms
- Alternate forms
- Gender differences
- Backgrounds
- Living Dex
- Custom user-created categories

COLLECTION UX

Build the collection experience around:

- A mobile-first, three-column sprite grid
- Full-color collected entries
- Clearly dimmed or silhouetted missing entries
- A different state for unreleased or category-ineligible entries
- A category selector for Normal, Shiny, Lucky, Hundo, XXL, and so on
- Search and filtering by name, Pokédex number, generation, region, type, form, and collection state
- Pokémon detail sheets with Collection, Wanted, and For Trade sections
- Form and costume galleries
- An explicit Quick Check mode for rapid one-tap toggling
- Immediate undo after a checklist change
- Touch targets of at least 44px
- Good keyboard and screen-reader accessibility
- Preservation of scroll position and active filters

Do not silently toggle collection state during ordinary browsing. One-tap toggling belongs in the clearly labeled Quick Check mode.

DATA MODEL

Use stable internal identifiers that do not depend on sprite filenames.

The catalog should distinguish:

- Pokémon species
- Forms
- Costumes
- Gender variants where relevant
- Collection categories
- Whether a category is eligible
- Whether a form/category is released in Pokémon GO
- Sprite asset references
- User collection records
- Wanted records
- Trade inventory or individual trade specimens

Keep collection records sparse: store meaningful user state rather than generating every Pokémon/category combination.

Trading inventory must support specimens with combined traits. For example, a single trade item may be Shiny + Costume + XXL. Do not flatten that into unrelated category totals.

Pokémon GO trade rules must be represented correctly:

- IVs reroll during trading, so a Hundo cannot be promised as a post-trade Hundo
- Lucky status is not transferred from an already Lucky Pokémon
- Shadow Pokémon cannot be traded

ASSETS

Use PokeMiners Pokémon GO sprite assets for this passion project.

Requirements:

- Build a maintainable asset manifest or synchronization pipeline
- Do not hard-code GitHub directory URLs throughout UI components
- Keep internal form identifiers independent from upstream filenames
- Lazy-load sprites
- Render only visible or nearby grid entries
- Provide missing-image fallbacks
- Add attribution and a clear unofficial/fan-project disclaimer
- Do not collect or request Pokémon GO account credentials
- Do not scrape private player data

For the first implementation, it is acceptable to use a small representative catalog slice while the import pipeline is being built, but the architecture must support the full Pokémon GO catalog without manually entering every Pokémon.

CSV IMPORT AND EXPORT

Design the import system early, even if the full importer lands after the first collection screen.

It must eventually support:

- Wide format, such as one row per Pokémon with category columns
- Long format, such as one row per Pokémon/category status
- Flexible column mapping
- Preview before applying changes
- Merge
- Replace
- Update-only
- Duplicate detection
- Unmatched Pokémon and form reporting
- Validation errors
- Automatic backup before import
- Rollback
- CSV export for portability

SEARCH STRING LAB

Create a first-class Search Lab with:

- My Missing
- Visual Builder
- Recommended Strings
- Saved Strings
- Resources and keyword reference

The builder should support:

- Pokémon GO-compatible search keywords
- AND, OR, and NOT logic
- Category and attribute filters
- Selecting visible Pokémon or forms
- Missing-only strings
- Pokédex number range compression
- Splitting strings that become too long
- Copy-to-clipboard
- Plain-language explanation of the generated string
- Clear distinction between exact matches and candidate/result-narrowing strings
- Saved and reusable templates

Treat search strings as two different workflows:

1. Reconciliation strings for checking Pokémon GO against this application
2. Trade and planning strings for narrowing in-game inventory

Do not imply that generated strings can perfectly prove every trait when Pokémon GO search syntax cannot represent it exactly.

TRADING

Prepare the data model for:

- Wanted lists
- For-trade inventories
- Public trainer profiles
- Comparing two trainers’ lists
- Mutual match results
- A future trading board
- Discord usernames or profile links
- Later Discord webhook or bot integration

Begin with safe contact links. Do not build automatic direct messaging until identity, abuse prevention, privacy, rate limiting, and consent have been designed.

PUBLIC AND PRIVATE DATA

The site will eventually be public, so separate:

- Public catalog data
- Private collection data
- Public profile data that a user deliberately shares
- Private contact and account data

Do not expose private collection or contact information by default.

Structure authentication and authorization so multiple users can be supported later. If authentication would block the initial visual MVP, implement a clearly documented local development user abstraction first, but do not expose unprotected production write endpoints.
